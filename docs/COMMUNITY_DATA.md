# Общественная база прохождения: данные отдельно от личного прогресса

## Что уже есть и чего нет

В `knowledge/` находится **локальная основа**, не запущенный общественный сервис:
версионированные Pydantic-модели, JSON Schema, валидатор и консервативное
сопоставление записей с результатами будущего проверенного парсера.
`knowledge/catalog.json` намеренно пуст. Никакие реальные предметы, места,
требования или флаги Belmont’s Curse не выдуманы и не добавлены.

Первый предметный приоритет — улучшения максимума HP и маны в Belmont’s Curse.
Пока нет подтверждённого списка предметов и проверенного парсера конкретной сборки,
нельзя обещать «все улучшения» или «какие уже взяты». Число найденных записей
также не доказывает полноту базы. Аналогичная база может отдельно собираться для
каждой игры; одна игра не наследует непроверенные знания другой.

## Где и как сообщество сможет собирать

Предлагаемый начальный процесс — отдельные каталоги по Steam AppID и точной
версии/сборке, хранящиеся в Git-репозитории, с изменениями через GitHub pull request.
Это **предложение процесса**, а не уже созданный репозиторий, опубликованная база
или открытый PR. На этом этапе всё остаётся локально. В дальнейшем веб-форма
может создавать черновик для того же review-процесса, но её сейчас нет.

1. Участник сообщает AppID, точную сборку, тип `hp_upgrade` / `mana_upgrade`,
   стабильный идентификатор записи и пишет собственное описание места и требований.
   Идентификатор не меняют при правках формулировок. Разные сборки держат в
   отдельных каталогах; перенос между ними требует повторной проверки mapping.
2. Добавляет источники с URL и атрибуцией, автора, основание прав
   `original` / `authorized` и явную лицензию данных. Для `authorized` нужна ссылка
   на разрешение. Ссылка на чужой гайд сама по себе не разрешает копировать текст,
   карты, скриншоты или видео. Не делаем массовый скрейпинг/копирование гайдов.
3. Отдельный reviewer проверяет описание места и требований. Оно может быть
   подтверждено даже тогда, когда сопоставление с сейвом ещё `unverified`.
4. Независимо проверяют каждый per-item флаг и условие допустимости напоминания:
   точная игра, сборка, ID и версия парсера, явное значение флага, воспроизводимое
   свидетельство и reviewer. Никаких догадок об offsets или значении байтов.
   Контрольное сравнение «до/после» выполняется локально с разрешения владельца;
   публично достаточно минимального обезличенного отчёта/синтетического теста.
   Нельзя публиковать реальные сейвы, имена аккаунтов, токены или пути пользователя.
5. Отдельно рецензируют spoiler-safe текст и условие его показа. `draft` никогда
   не обслуживается как подсказка. В первой версии разрешена только исходная
   нейтральная фраза пользователя: **«не забудь осмотреться»**.
6. Запускают валидацию и тесты; только после review владелец репозитория может
   принять изменение. Значение `verified` в JSON — утверждение reviewer,
   не автоматическое доказательство: доверие устанавливает review-процесс.
   Непроверенные PR нельзя напрямую подключать к игровому советчику.

Лицензия кода MIT **не является выбором лицензии общественных данных**.
До публикации нужно отдельно утвердить лицензию базы и правила вкладов;
совместимость каждого вклада проверяется отдельно. Значение поля `license`
валидатор проверяет как обязательное, но не выдаёт юридическое разрешение.

## Контракт 1.0

Источник схемы — `knowledge/models.py`, экспорт — `knowledge/schema.json`.
Каталог содержит `schema_version: "1.0"` и `records`. Каждая запись содержит:

- `id`, `appid`, `game_version`, `object_type`, `synthetic`;
- `full_location`: полное место, инструкция, требования и ссылки на другие
  записи текущей игры/сборки; это **спойлерные** открытые справочные данные;
- `sources` и `rights`: источники, атрибуция, авторство/разрешение, лицензия;
- `collection_mapping`: необязательный индивидуальный флаг, точная версия
  парсера и отдельный review со свидетельствами;
- `safe_hint`: необязательная отдельно проверенная оригинальная нейтральная
  фраза и отдельно подтверждённый trigger типа `hint_eligibility`.

Валидатор отклоняет неизвестные поля, неправильные типы, дубликаты ID,
неразрешённые ссылки, cross-game/build ссылки и `verified` без reviewer/источников.
Он не может автоматически определить истинность источника, авторское право или
безопасность произвольного текста. Поэтому свободный текст безопасных подсказок
в версии 1.0 запрещён; расширение потребует отдельного дизайна и review.

## «Взято / не взято / неизвестно»

`collection_status(record, evidence)` возвращает:

- `collected`: подтверждённый per-item mapping и явный флаг соответствует
  значению «взято»;
- `not_collected`: тот же mapping и явный противоположный boolean;
- `unknown`: нет mapping, нет флага, не совпадает игра/сборка/парсер/его версия,
  нет подтверждённого review или нет доверенного результата парсера.

Отсутствующий флаг **не равен false**. Суммарные HP/мана, время игры,
достижения и метаданные файла не идентифицируют конкретные улучшения.
`ParserEvidence` принимает только явные boolean-флаги, а не числовые агрегаты.
Будущий адаптер обязан выдавать только проверенные индивидуальные флаги;
нельзя переименовать агрегат HP в boolean и считать его доказательством.

`safe_hint_view(record, evidence)` выдаёт только `{"text": "не забудь осмотреться"}`,
если место проверено, текст reviewed, предмет явно `not_collected` и проверенный
trigger явно сработал в том же результате парсера. Иначе возвращает `None`.
В ответе нет ID, типа улучшения, места, требований, источников или будущих событий.
Даже для уже известных предметов v1 намеренно не расширяет этот ответ.
Полный каталог не следует передавать модели/клиенту как «безопасную подсказку».
При выводе нескольких результатов будущий адаптер должен убирать дубликаты
нейтральной фразы и не раскрывать число скрытых предметов.

## Граница доверия и дальнейшее подключение

Эти функции — локальная библиотека, пока **не подключённая** к серверу, UI или MCP.
`verified` в `ParserEvidence` должен выставляться только доверенным локальным
адаптером после успешного разбора текущего выбранного сейва. Нельзя принимать это
поле от произвольного API-клиента как удостоверение. Проверка свежести снимка,
пользователя/слота, разрешений и отзыв доступа — обязанность будущего адаптера.
При любой ошибке чтения/неподдерживаемой сборке он должен не выдавать evidence,
а не подставлять нулевые значения или предыдущий результат без предупреждения.
Реального декодера, подтверждённых offsets и схемы сейва здесь нет.

Все примеры в `tests/test_knowledge.py` явно синтетические: вымышленная игра,
вымышленные предметы/комната/флаги, `example.invalid`, лицензия `TEST-ONLY`.
Их нельзя переносить в реальные каталоги или считать данными Belmont.

```sh
cd game-assist
python -m knowledge knowledge/catalog.json
python -m unittest discover -s tests -p test_knowledge.py -v
```

Успешный валидатор подтверждает **форму**, не полноту и не фактическую истинность
базы. Чтобы начать реальные вклады, нужны авторизованные источники/собственные
наблюдения, точная сборка игры, review и отдельное решение о публикации данных.
