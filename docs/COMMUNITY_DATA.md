# Общественная база прохождения: данные отдельно от личного прогресса

## Что уже есть и чего нет

В `knowledge/` находится **локальная основа**, не запущенный общественный сервис:
версионированные Pydantic-модели, JSON Schema, валидатор и консервативное
сопоставление записей с результатами будущего проверенного парсера.
`knowledge/catalog.json` намеренно пуст. Никакие реальные предметы, места,
требования или флаги Belmont’s Curse не выдуманы и не добавлены.

Первый предметный приоритет — улучшения максимума HP и маны в Belmont’s Curse.
Пока нет подтверждённого списка предметов и проверенного парсера конкретной сборки,
нельзя обещать «все улучшения» или «какие уже взяты». Число найденных записей
также не доказывает полноту базы. Аналогичная база может отдельно собираться для
каждой игры; одна игра не наследует непроверенные знания другой.

## Где и как сообщество сможет собирать

Предлагаемый начальный процесс — отдельные каталоги по Steam AppID и точной
версии/сборке, хранящиеся в Git-репозитории, с изменениями через GitHub pull request.
Это **предложение процесса**, а не уже созданный репозиторий, опубликованная база
или открытый PR. На этом этапе всё остаётся локально. В дальнейшем веб-форма
может создавать черновик для того же review-процесса, но её сейчас нет.

1. Участник сообщает AppID, точную сборку, тип `hp_upgrade` / `mana_upgrade`,
   стабильный идентификатор записи и пишет собственное описание места и требований.
   Идентификатор не меняют при правках формулировок. Разные сборки держат в
   отдельных каталогах; перенос между ними требует повторной проверки mapping.
2. Добавляет источники с URL и атрибуцией, автора, основание прав
   `original` / `authorized` и явную лицензию данных. Для `authorized` нужна ссылка
   на разрешение. Ссылка на чужой гайд сама по себе не разрешает копировать текст,
   карты, скриншоты или видео. Не делаем массовый скрейпинг/копирование гайдов.
3. Отдельный reviewer проверяет описание места и требований. Оно может быть
   подтверждено даже тогда, когда сопоставление с сейвом ещё `unverified`.
4. Независимо проверяют каждый per-item флаг и условие допустимости напоминания:
   точная игра, сборка, ID и версия парсера, явное значение флага, воспроизводимое
   свидетельство и reviewer. Никаких догадок об offsets или значении байтов.
   Контрольное сравнение «до/после» выполняется локально с разрешения владельца;
   публично достаточно минимального обезличенного отчёта/синтетического теста.
   Нельзя публиковать реальные сейвы, имена аккаунтов, токены или пути пользователя.
5. Отдельно рецензируют spoiler-safe текст и условие его показа. `draft` никогда
   не обслуживается как подсказка. В первой версии разрешена только исходная
   нейтральная фраза пользователя: **«не забудь осмотреться»**.
6. Запускают валидацию и тесты; только после review владелец репозитория может
   принять изменение. Значение `verified` в JSON — утверждение reviewer,
   не автоматическое доказательство: доверие устанавливает review-процесс.
   Непроверенные PR нельзя напрямую подключать к игровому советчику.

Лицензия кода MIT **не является выбором лицензии общественных данных**.
До публикации нужно отдельно утвердить лицензию базы и правила вкладов;
совместимость каждого вклада проверяется отдельно. Значение поля `license`
валидатор проверяет как обязательное, но не выдаёт юридическое разрешение.

## Контракт 1.0

Источник схемы — `knowledge/models.py`, экспорт — `knowledge/schema.json`.
Каталог содержит `schema_version: "1.0"` и `records`. Каждая запись содержит:

- `id`, `appid`, `game_version`, `object_type`, `synthetic`;
- `full_location`: полное место, инструкция, требования и ссылки на другие
  записи текущей игры/сборки; это **спойлерные** открытые справочные данные;
- `sources` и `rights`: источники, атрибуция, авторство/разрешение, лицензия;
- `collection_mapping`: необязательный индивидуальный флаг, точная версия
  парсера и отдельный review со свидетельствами;
- `safe_hint`: необязательная отдельно проверенная оригинальная нейтральная
  фраза и отдельно подтверждённый trigger типа `hint_eligibility`.

Валидатор отклоняет неизвестные поля, неправильные типы, дубликаты ID,
неразрешённые ссылки, cross-game/build ссылки и `verified` без reviewer/источников.
Он не может автоматически определить истинность источника, авторское право или
безопасность произвольного текста. Поэтому свободный текст безопасных подсказок
в версии 1.0 запрещён; расширение потребует отдельного дизайна и review.

## «Взято / не взято / неизвестно»

`collection_status(record, evidence)` возвращает:

- `collected`: подтверждённый per-item mapping и явный флаг соответствует
  значению «взято»;
- `not_collected`: тот же mapping и явный противоположный boolean;
- `unknown`: нет mapping, нет флага, не совпадает игра/сборка/парсер/его версия,
  нет подтверждённого review или нет доверенного результата парсера.

Отсутствующий флаг **не равен false**. Суммарные HP/мана, время игры,
достижения и метаданные файла не идентифицируют конкретные улучшения.
`ParserEvidence` принимает только явные boolean-флаги, а не числовые агрегаты.
Будущий адаптер обязан выдавать только проверенные индивидуальные флаги;
нельзя переименовать агрегат HP в boolean и считать его доказательством.

`safe_hint_view(record, evidence)` выдаёт только `{"text": "не забудь осмотреться"}`,
если место проверено, текст reviewed, предмет явно `not_collected` и проверенный
trigger явно сработал в том же результате парсера. Иначе возвращает `None`.
В ответе нет ID, типа улучшения, места, требований, источников или будущих событий.
Даже для уже известных предметов v1 намеренно не расширяет этот ответ.
Полный каталог не следует передавать модели/клиенту как «безопасную подсказку».
При выводе нескольких результатов будущий адаптер должен убирать дубликаты
нейтральной фразы и не раскрывать число скрытых предметов.

## Граница доверия и дальнейшее подключение

Эти функции — локальная библиотека, пока **не подключённая** к серверу, UI или MCP.
`verified` в `ParserEvidence` должен выставляться только доверенным локальным
адаптером после успешного разбора текущего выбранного сейва. Нельзя принимать это
поле от произвольного API-клиента как удостоверение. Проверка свежести снимка,
пользователя/слота, разрешений и отзыв доступа — обязанность будущего адаптера.
При любой ошибке чтения/неподдерживаемой сборке он должен не выдавать evidence,
а не подставлять нулевые значения или предыдущий результат без предупреждения.
В этой библиотеке нет декодера. Отдельный `decoders/belmont.py` теперь читает
четыре структурных scalar-поля формата `1.1.3`; подтверждённых pickup mapping
и HP/mana-локаций по-прежнему нет (см. `PARSER_COVERAGE.md`).

Все примеры в `tests/test_knowledge.py` явно синтетические: вымышленная игра,
вымышленные предметы/комната/флаги, `example.invalid`, лицензия `TEST-ONLY`.
Их нельзя переносить в реальные каталоги или считать данными Belmont.

```sh
cd game-assist
python -m knowledge knowledge/catalog.json
python -m unittest discover -s tests -p test_knowledge.py -v
```

Успешный валидатор подтверждает **форму**, не полноту и не фактическую истинность
базы. Чтобы начать реальные вклады, нужны авторизованные источники/собственные
наблюдения, точная сборка игры, review и отдельное решение о публикации данных.

## Универсальное расширение профилей (2026-10-31)

Реализован отдельный декларативный контракт `knowledge/profiles.py` и его
JSON Schema `knowledge/profile_schema.json`; `knowledge/game_profiles.json`
содержит три приоритетные identity-записи: Belmont `4231820`, Elden Ring `1245620`,
The Witcher 3 `292030`. `approved` означает принятие **описания**, не автоматический
запуск парсера и не разрешение доступа к аккаунту. Любой другой корректный AppID
может получить свой профиль; отсутствие записи означает неизвестные возможности,
а не запрет на регистрацию игры в аккаунте.

Только у Belmont описаны четыре уже реализованных scalar-поля для save-format
`1.1.3`, с SHA-256 текущего исходника reader и ссылками на review, synthetic tests
и ранее составленный отчёт об авторизованной private fixture проверке. Точный
**game build остаётся unknown**. Fragment counters не признаны количеством
завершённых улучшений; currentHealth/currentMana не являются максимумами.
Pickup IDs, HP/mana-места, inventory, quests, bosses и missables не подтверждены.
У Elden Ring/Witcher gameplay coverage остаётся unknown. Процент покрытия не задан.

`load_registry()` валидирует локальный JSON, отсекает файлы больше 1 MiB,
дубли JSON keys, неподдерживаемую версию схемы/типы capabilities/поля и неполные
свидетельства. `approved_profile(appid)` возвращает только approved metadata;
`coverage_for(...)` требует точного совпадения версии/формата и возвращает `None`
при неизвестном или неподдерживаемом случае. Произвольный `parser_id` — только
символьное имя: реестр не импортирует модули, не открывает evidence paths,
не ходит по source URLs и не исполняет вклад сообщества. Runtime adapter обязан
отдельно проверить доступ, текущий сейв и соответствие pinned revision своему
встроенному reader. Сам реестр не является криптографически подписанным trust root.

Реализованы локальная схема/валидатор/metadata registry и тесты. Модерация сайта,
публичный GitHub intake, автоматический release pipeline и установка community
парсеров **не реализованы**. Процесс вкладов: [CONTRIBUTING.md](../CONTRIBUTING.md).

## BEL-01: протокол controlled save-diff (подготовка, не подтверждённый mapping)

Добавлены `knowledge/save_diff_evidence.py`, пустой
`knowledge/evidence_template.json`, схема `knowledge/evidence_schema.json`
и synthetic negative tests. Это формат **обезличенного отчёта наблюдений**, не
парсер сейва, не сборщик файлов и не автоматическое подтверждение игрового смысла.
Локальный baseline Belmont сам по себе не подтверждает ни один pickup.
Реальные новые пары/действия пользователя в этой разработке не запрашивались.

### Протокол будущей разрешённой проверки

1. До чтения фиксируют разрешение владельца на **конкретные локальные копии**,
   before/after порядок, точный game build, платформу, save-format, выбранный
   слот/прохождение и ревизию read-only парсера. Неизвестный build не заменяют
   версией формата `1.1.3`. В публичный отчёт не включают название персонажа,
   SteamID, slot ID, пути, имена файлов, raw JSON или entity IDs.
2. Отдельный локальный журнал (не PR) хранит выбранные пути и SHA-256 исходников.
   Снимки должны быть стабильны; оригиналы не изменяются. Нельзя искать другие
   файлы или запускать игру/редактор без отдельного разрешения. Никакие файлы
   не прикладываются автоматически к community contribution.
3. Сначала неизменный **control**, затем **одно** самостоятельно выполненное
   пользователем действие HP/mana pickup и независимое наблюдение в самой игре.
   Отдельно записывают расход текущего ресурса, изменение явно наблюдаемого
   максимума, fragment counter и потенциальный индивидуальный флаг. Не смешивают
   несколько pickups, смену слота, autosave, трату ресурса или случайные события.
4. Действие повторяют только в разрешённой сопоставимой ситуации с новым
   before/after и control. Повтор должен наблюдать те же категории и направление
   изменений; изменившийся control или противоречащий повтор блокирует review.
   Неповторимый одноразовый pickup без сопоставимого подтверждения остаётся
   гипотезой; протокол не предписывает менять/откатывать сейв или играть за человека.
5. Локальный structural diff должен сохранять типы и точность, различать absent,
   null, boolean/number/string, отклонять duplicate JSON keys и не сортировать
   массивы. Изменение индекса/порядка массива без проверенного стабильного ID —
   позиционное различие, не доказательство изменения множества entities.
   Эти детали анализируются **локально**; публичная схема принимает только
   категорию поля/изменения и качество correspondence, без точных JSON pointers
   и приватных before/after значений. Отчёт не заменяет сам diff-инструмент.
6. Сначала `hypothesis`. Независимый reviewer проверяет разрешённые свидетельства,
   control/repeat, ground truth, противоречия и редактирование персональных данных.
   Только maintainer может записать псевдоним reviewer и opaque review reference
   в `review_attestation` и отметить `verified` в узком scope
   `structural_observations_only`. Валидатор проверяет полноту полей,
   **не подлинность reviewer и не фактическую истинность утверждений**.
   Недоверенный PR не становится trusted evidence от одного self-tag `verified`.

### Что реализованный валидатор гарантирует и чего нет

- `review_blockers()` перечисляет отсутствие точной версии, неподдерживаемый
  формат, consent/redaction/ground-truth gates, отсутствие action/control/repeat,
  confounders, позиционный шум, изменившийся control и несовпадающий repeat.
  Пустой список означает готовность к **человеческому review**, не verified.
- В этом срезе поддерживаемый scope — Belmont AppID `4231820`, JSON format
  `1.1.3`; другой AppID/формат остаётся unknown/blocked, не нулевой прогресс.
- `public_projection()` выкидывает optional `private_pair` hashes даже из обычной
  сериализации, не включает raw values/paths/entity IDs и всегда оставляет
  `semantic_mapping_status` и `collected_item_status` равными `unknown`.
  Сам объект модели локально может содержать optional hashes: не публикуйте
  входной JSON напрямую. Публикуется только отрецензированная проекция.
- Увеличение currentHealth не доказывает максимум HP; fragment counter не
  доказывает конкретный взятый предмет. Даже поле, названное maximum_health,
  или candidate_item_flag не становится подтверждённой механикой по названию.
- Этот модуль не читает сейвы, не загружает ссылки, не выполняет код community,
  не создаёт FlagMapping/ParserEvidence и не выдаёт подсказки. Существующие
  knowledge/catalog/profile контракты не меняются. Для BEL-02/03 нужны отдельные
  реальные controlled evidence, семантический review и правомерная запись.

Проверка после включения файлов в репозиторий:

```sh
python -m unittest discover -s tests -p test_save_diff_evidence.py -v
python -m compileall -q knowledge/save_diff_evidence.py
```

Template не содержит реальных наблюдений или private fixture. Синтетические
тесты проверяют лишь контракт и негативные случаи, не закрывают BEL-01 приёмку
на реальных данных и не доказывают готовность «всех улучшений».
